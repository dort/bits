# Fibonacci through magic sets

`fib.mm2` is a Fibonacci relation consumed by the reusable transformer in
`../magic_sets/`. It defines `F(0) = 0`, `F(1) = 1`, and
`F(n) = F(n-1) + F(n-2)`, where `n` is the requested index and `F(n)` its value.
The transformer automatically emits the magic guards and predecessor-demand
rules. All predecessor arithmetic, comparisons, and additions execute through
MORK's Rust-backed `pure` sink. Python only validates and assembles requests,
invokes MORK, and displays results.

```bash
./run.sh                         # F(10)
./run.sh 0 1 10 20 92            # several queries, with shared subproblems
./run.sh 10 --show magic         # demand facts generated by the transformation
./run.sh 10 --show rules         # rewritten program, including arithmetic
./run.sh 10 --show derived --stats
python3 -B test.py
```

For example, `./run.sh 10` returns:

```scheme
(result fib-10 (atom fib (cons 10 (cons 55 nil))))
```

Supported indices are integers from **0 through 92**. `F(92)` is
`7540113804746346429`; the next Fibonacci value exceeds signed 64-bit range.
Requests outside that range fail before running MORK. The shared arithmetic
implementation also checks for overflow, including when called independently
of this runner. `MORK=/path/to/mork` selects a runtime; the default is the
existing `../../../MORK/target/release/mork` checkout. Python 3.8+ is required
for the runner and tests, with no additional packages.

## What the magic sets do

Each query binds the Fibonacci index and leaves the result free: the `bf`
adornment, represented as `(cons b (cons f nil))`. The seed for index 10 is:

```scheme
(magic fib (cons b (cons f nil)) (cons 10 nil))
```

The generated demand rules propagate to predecessor indices, under the same
`n >= 2` guard as the recursive rule. The second recursive call also includes
the first call in its demand-rule prefix, following the transformer's written
left-to-right evaluation order. Each completed Fibonacci tuple is retained and
reused by other callers.

Requesting only index 10 creates 11 demand facts and 11 Fibonacci tuples, for
indices 0 through 10. It does not compute values for indices 11 through 92.
Requesting only 0 or only 1 derives only that base case. Multiple queries share
their demand and result relations; duplicate requests return one result.

The source contains a finite `index` relation covering 0 through 92. Those facts
are only the legal indices, not Fibonacci answers or precomputed additions.
Placing `index(n)` first makes the original program valid for ordinary bottom-up
evaluation too. The transformed rule places its magic guard before `index(n)`,
so the query's bound index restricts that join. The plain engine computes all
93 Fibonacci tuples and serves as a comparison in the tests.

## Run directly in MORK

The source and example queries are separate files. From this directory:

```bash
../../../MORK/target/release/mork run example.mm2 \
  --aux-path fib.mm2 \
  --aux-path ../magic_sets/magic_engine.mm2 \
  --aux-path ../magic_sets/common.mm2 \
  --aux-path ../magic_sets/builtins.mm2
```

This prints the entire MM2 space. The bundled example requests indices 10 and
20, producing values 55 and 6765. To supply a different query, use the shape
`(query ID (atom fib (cons (c INDEX) (cons (v value) nil))))`, where `ID` is a
unique query identifier and `INDEX` is its bound index. The convenience runner
checks indices; raw MORK execution uses the finite relation and gives no answer
for an out-of-domain index. No Peano representation or depth counter is used.

The tests compare values with an independent integer recurrence, cover both base
cases and the largest supported value, verify demand restriction and sharing,
compare with full closure, and reject invalid requests. The shared magic-sets
suite separately checks arithmetic failures and the generic transformation.
